# 0001 · Reach the emulator through a byte-level C ABI

**Status**: Accepted

## Context

aws-emulator runs in two modes. Its standalone server is usually run as a Docker image and serves HTTPS, so a JVM test
pays for a container, a self-signed certificate added to a trust store, and a free port, on every run. Its embedded
mode runs in-process, but it works by handing a Rust SDK an in-process HTTP client, so only Rust callers can use it.

A JVM test needs the embedded mode's shape without being written in Rust.

## Decision

`emu-core` links the services into a `cdylib` and exports four `extern "C"` functions. A request crosses as a method,
a URI, a block of `name: value\r\n` header lines and a body. The response comes back as a status code and two buffers.

## Alternatives

A **struct per header** across the ABI
:   Typed, but every host would need to build and walk arrays of structs. Header lines are trivial to produce and
    parse in any language, and the framing rule (no CR or LF in a line) is easy to enforce on the way in.

**Serialized HTTP/1.1** on the wire
:   One buffer instead of four arguments, but the host would have to write and parse HTTP, including chunking and
    edge cases the SDK already handles.

A **loopback socket** to the standalone server, in-process
:   Avoids Docker, but keeps the port and the TLS trust store, which are the parts that fail.

## Consequences

- Any host that can call C can use the emulator. The JVM binding is one; the Rust tests are another.
- Bodies are buffered whole, and nothing streams. That suits tests; it does not suit very large objects.
- Panics must not unwind across the boundary, so every entry point catches them and reports a value instead.
